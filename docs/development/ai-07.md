# AI-07: exact confirmed actions

Updated: 2026-10-26.
Status: implemented locally; default-disabled and unactivated. Migration `0031_ai_action_proposals`
is for the existing reviewed AI migration chain. Do not migrate or restart the running application
or enable real providers as part of development verification.

## Owner-approved scope

The owner selected the complete AI-07 scope, one confirmation for a related batch, and delegated
proposal lifetime to implementation judgment. Lifetime is 24 hours in PostgreSQL. Waiting creates
no model requests, running agent, held database connection or per-proposal background job.

Supported operations are `page_create`, `page_update`, `event_create`, `event_update` and
`reminder_create`. They use `NoteService`, `CalendarService` and `ReminderService` in a common
caller-owned transaction. Independent pages/events need no academic profile.

Automatic grants/dispatch, tasks/planning, deletes, official-event edits, database and relationship
writes remain outside this slice. Personal-event overlap is allowed by the existing service;
AI-07 does not implement availability, conflict-free scheduling or the P-06 planner.

## Proposal and framework bridge

The optional typed `propose_actions` tool takes one discriminated batch of 1–8 operations, with
at most 16 KiB of arguments. This is an individual execution/transport bound, not a user allowance.
Related actions must be in the same call. Unknown operations/fields, owner overrides, naive/numeric
timestamps and ambiguous reminder references are rejected.

LangChain `HumanInTheLoopMiddleware` pauses that tool before dispatch. The tool itself cannot write
business data. The application validates current sources/targets and persists an immutable batch,
exact before/after effects, source references, timezone, creation/expiry timestamps and a digest.
The run completes with a review message, releasing the runner/checkpoint connection. A new proposal
supersedes older pending proposals in that chat; changing arguments always requires a new preview.

The authenticated decision endpoint executes the stored batch, never model-supplied approval flags
or replacement arguments. Confirmation does not invoke a model or resume a business-write tool.
On the next message, a fresh runner reads the durable proposal outcome, completes the pending HITL
state with LangGraph's `update_state` and starts the new turn. Historical proposal arguments are
removed from the live continuation. An unavailable proposal cannot be recovered as permission.
Graph checkpoints provide continuity; the application transaction and receipt provide commit truth.

A crash before proposal persistence cannot authorize writes. A proposal from a run that failed or
was cancelled before completing cannot execute. A later cancellation/provider failure cannot undo
an already committed outcome. Duplicate/concurrent decisions return the first stored outcome.

## Exact previews and business rules

- New pages include the exact title, typed block document and optional owned active parent.
  Parent identity/version/title are included in the preview when selected.
- Page updates require the current page version and show the full original/result documents.
  Existing block IDs and types must remain present; additions and content/reordering changes are
  supported, while block removal/type conversion is intentionally unavailable in this slice.
  Whole-page deletion, moving existing pages and Markdown flattening are not action operations.
  `read_page` includes a typed document when it fits a 10 KiB bound; individual block reads retain
  their existing scope. Large edits must fit the tool bound; they are never silently truncated.
- Events use exact offset-aware start/end, title, description, location and `blocks_time`.
  Event updates require the existing version and sparse `changes`; omitted fields, including
  descriptions and locations absent from calendar summaries, are preserved across durable reloads. Relative dates resolve before preview using profile
  time; stored dates never move automatically when confirmation is delayed.
- Reminders use an accessible personal/official target and explicit minutes before its start.
  An `event_action` is the zero-based index of an earlier event create/update in the same batch.
  Referencing an independently edited event by ID in that batch is rejected; use `event_action`
  so the confirmed trigger matches the final start. Existing reminder behavior is preserved:
  moved/skipped/withdrawn targets cannot deliver obsolete reminders. Moves show a warning that
  existing reminders will be cancelled; replacement reminders require an explicit batch action.
- Missing duration/time or materially ambiguous targets must be clarified before a proposal.
  All product previews use profile timezone and display the exact reminder trigger.

Confirmation locks the active owner, checks chat lifetime, completed originating run, current
capabilities/connection status, timezone, source truth, target versions and business preconditions.
Calendar evidence includes an additive fingerprint of resolved facts, because official source
rows have no monotonic revision. This rejects changed official times even when their numeric
version remains unchanged. Canonical owner locking serializes the selected modules' writes. Referenced official schedule rows
are held with shared locks while reminder/source truth is checked and committed, preventing a
concurrent official update from slipping between validation and write. No network/model call occurs
under these locks. Source validation uses current ordinary application reads, including pagination.

All actions and their content-free execution receipt commit together. Any changed precondition
applies nothing and requires a new preview. Database/commit failures roll everything back. There
is no partial-success mode and no splitting a batch across model turns. Preview payloads have a
2 MiB storage/transport bound; oversized previews are refused without truncation.

## API and UI

All routes require an active completed-registration browser session and `Cache-Control: no-store`.
Decision writes additionally require the existing exact Origin and CSRF checks. Ownership is
server-derived; missing/foreign proposals share 404. `AI_ENABLED=false` or
`AI_ACTIONS_ENABLED=false` prevents action admission/confirmation. Both settings default to false.

| Method | Route | Contract |
| --- | --- | --- |
| GET | `/api/v1/ai/conversations/{id}/proposals?limit=20&offset=0` | Owned current/terminal previews, descending creation/ID order; limit 1–100 |
| POST | `/api/v1/ai/proposals/{id}/decision` | `{digest, decision: approve | reject}`; exact digest required; stored outcome on replay |

Responses expose proposal/run IDs, digest, creation/expiry, status, timezone, effects, outcomes
and source references. Internal batch and framework interrupt state are not public fields.
Expired pending previews are returned with `status=expired`; a decision at the exact expiry cannot
execute. Changed capabilities/versions/sources return a safe conflict/error without mutation.

The chat renders Russian before/after cards, exact local dates/triggers, movement warnings and
one Apply all/Reject pair. Completed outcomes can open the page or current event/reminder target.
Reloading fetches stored state. Confirmation buttons are disabled during a new active run and
while a decision is in flight. A local expiry timer refetches once when necessary; there is no
continuous proposal polling. Plain text/block previews do not interpret injected HTML.

## Storage and retention

`ai_action_proposals` stores chat-owned content with owner-constrained conversation/run foreign
keys, one proposal per run, a fixed 24-hour expiry and bounded JSONB payload. Expiry is checked on
access/decision independently of maintenance. Content follows the chat/30-day activity lifecycle:
chat deletion/expiry and run activity cleanup cascade proposal payloads. Expiry does not keep a
runner or lock alive; it is a timestamp comparison. A shorter confirmation window would not
reduce the established chat/checkpoint retention or model usage.

`ai_action_receipts` stores only owner/proposal IDs, terminal status, operation/target IDs and
completion timestamp. It contains no prompt, title, document or preview body. It is independent
of chat/proposal cleanup and retained until account deletion. Deleting a chat preserves committed
business objects and receipts; unknown/expired/deleted IDs cannot recreate proposals or writes.
The migration refuses downgrade while proposal content or receipts remain.

## AI-10 extension (2026-10-29)

The original slice above describes AI-07 delivery and dated verification. AI-10 now
adds `task_create`, `task_update` and `task_plan_apply` through the same framework
review and shared transaction path, plus authenticated `POST /proposals/{id}/revise`
under `/api/v1/ai`. Revision creates a new preview/digest and supersedes the old one;
confirmation remains a separate request. Source evidence and current versions must
still validate. Task creation stores provenance independently of chat retention.
Plan preview/application, partial acceptance, integrity checks and browser controls
are documented in [task planning](task-planning.md) and [AI-10](ai-10.md).
