# AI-11: Labeled Knowledge Fallback and Public Web Search

Status: implemented locally; web search is disabled by default and unactivated.
No real provider requests, application deployment, secret changes or production
migrations are included. Owner clarification: 2026-10-29.

## Chat behavior

The ordinary assistant answers workspace questions from relevant owned materials
first. If the evidence is insufficient it can call `search_web` automatically,
without a separate feature screen or per-search confirmation. It distinguishes
**Из твоих материалов**, **Из интернета** and **Общие знания модели** in its
instructions; web citations also have a server-provided origin in the existing UI.
General questions need not scan unrelated private records. A failed read or pending
index is disclosed, never interpreted as confirmed absence of information.

An explicit source selection restricts local retrieval. Natural-language instructions
to use only documents prohibit web/model fallback in the assistant policy. The
additive `source_only: true` message field also enforces no external dispatch on
the server and participates in submission idempotency. It requires no new UI step.
Complete-source document processing retains its existing local-source-only tools;
ordinary follow-up questions can combine its revalidated evidence with web search.

Answer wording and whether evidence is sufficient remain model decisions. Synthetic
models verify plumbing/policies, not real-model compliance, answer quality or truth.
A retrieved reference proves provenance, not that every generated claim is correct.

## Provider boundary and personal credentials

`search.application.web.WebSearch` owns the bounded query/result contract. The
agent uses that contract rather than DeepSeek-specific model tools. Another search
adapter can implement it without changing workspace retrieval, citation storage or
chat presentation. This does not claim arbitrary API accounts are supported today:
current model/personal connections support OpenRouter; additional providers need
verified adapters and connection configuration.

The delivered adapter uses the documented OpenRouter `openrouter:web_search` server
tool in an isolated request. Only the minimal public search terms and a fixed search
instruction are sent, never the chat history, local tool bodies or documents. The
selected conversation's exact model and credential are reused explicitly: an owner
personal OpenRouter connection stays personal; there is no fallback to the operator
key, another model or another search engine. Connection ownership/version/disconnect
and run state are checked again at actual dispatch.

The search engine is pinned to Exa `fast`, independently of the answering model's
native search support. A future provider can use the same application tool through
its own adapter. The ordinary model transport still forbids hosted plugins; only
this isolated search request enables the single allowlisted server tool.

Contract evidence checked on 2026-10-29:
[OpenRouter search server tool](https://openrouter.ai/docs/guides/features/server-tools/web-search)
documents engine selection, result/content/tool-call bounds and URL annotations.
The adapter uses returned `url_citation` content, URLs and titles; it never promotes
the isolated model's generated prose to retrieved evidence. Missing usable
annotations mean **unavailable**, not a proven empty search. The neutral port can
represent a verified **not_found** result for adapters that actually prove no match.
Server tools are beta; live compatibility with a selected endpoint/account is unverified.

## Bounds, citations and lifecycle

- One distinct search dispatch per foreground request, at most five results,
  512 query characters, 1,200 excerpt characters per result and the existing
  16 KiB tool-result envelope. Repeated identical calls use the current request's
  evidence; a second distinct query returns a limit outcome. The isolated server
  request permits one search tool execution and at most 256 output tokens.
- The isolated request also consumes a normal durable provider attempt, connection
  admission and the existing run budget. Provider token counts are preserved.
  Search fees are additional and are not fabricated from model token prices.
  Run/usage responses expose `unpriced_web_searches`; the usage UI states that its
  estimate excludes search fees. Tool invocation counts are conservative possible
  search-fee exposure, including denied/failed tool calls, not an invoice.
- Only the fixed HTTPS OpenRouter endpoint is requested. No arbitrary result URL is
  fetched by the application. Redirects/proxies, compressed responses, oversized
  bodies and transport deadlines are bounded/rejected. Citation validation blocks
  credentials, non-HTTP schemes, internal host suffixes, nonstandard ports and
  private/reserved IP literals. It is not a DNS-rebinding-safe general fetcher.
- Query validation rejects URLs, email addresses, obvious credentials and multiline
  dumps; the model policy requires minimal public terms and no private context.
  This is not a general-purpose private-data classifier.
- Web references store `source=web`, URL, retrieval time and a stable URL hash in the
  existing message/proposal JSON. Local reference shapes remain compatible. The
  source viewer identifies external origin and opens only a validated link without
  referrer information; it does not call the local-source read API for web references.
- Previous-turn web excerpts and source-derived answers are omitted from model
  context; the model must search again for fresh web evidence. Cancellation/deletion
  rechecks prevent late results from being published. Exact confirmed actions can
  preserve web citations as retrieval snapshots; external pages are not fetched
  under the mutation transaction and do not establish private state or permission.

## Activation

The catalog's additive `web_search` field defaults to **false**. The example keeps
it false. To configure a separately approved activation, use a new version of an
allowlisted tool-capable, non-`free_only` OpenRouter offering with `web_search: true`.
Both operator and personal connections follow the existing selection rules. A
free-only offering cannot silently acquire paid search. Disabling the capability
or disconnecting the selected connection prevents a new actual search dispatch.

AGENTS.md requires concrete bounded owner approval before coding-agent calls to
real search/LLM accounts, including free quota. Existing keys and this local stage
are not that approval. No key was read to check setup.
