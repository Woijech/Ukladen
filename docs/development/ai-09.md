## Acceptance evidence

Local checks exercise actual services/framework/adapters with synthetic inputs and
mocked provider transport. They prove boundaries and recovery, not that a real model
chooses the right tool or writes a good summary. The live record must identify model,
fixture revision, actual attempts/usage, observed outputs, reviewer decisions and all

## Synthetic suite and review tool

The versioned [40-case suite](../../apps/backend/tests/fixtures/ai/ai-09.json) contains
self-contained synthetic setups, user requests, expected/forbidden outcomes and critical
case markers. The two 20-case splits each have 14 Russian and 6 English requests.
Task/planning requests check honest unavailability; they do not require future tools.

From `apps/backend`, create a pending review without network access:

```bash
.venv/bin/python -m benchmarks.ai_acceptance > /tmp/ukladen-ai09-review.json
```

The template defaults to `mode=offline`, all decisions unreviewed and usage unknown.
After an explicitly approved live run, record exact provider/model, reviewer and approval
reference; capture each observed output/tool/business outcome, reviewer rationale, critical
failures and actual attempts/tokens. Keep raw live review records private and out of Git.
Then score the supplied human review (this command itself never calls a model):

```bash
.venv/bin/python -m benchmarks.ai_acceptance --results /tmp/ukladen-ai09-review.json
```

Exit 0 means a supplied live review meets the quality gate; exit 2 means incomplete,
offline or blocked; exit 1 means invalid input. All 40 records must be reviewed, at least
36 must pass, all critical cases must pass and no critical failure may be recorded in
any case. Each record needs observed evidence and notes; missing/duplicate/unknown IDs,
changed fixture hashes and invalid usage are refused. Offline scores always say
`quality_gate=not_evaluated`, even with 40 scripted passes. A review file is human evidence,
not an authenticity verifier, provider authorization or application release approval.

## Compatibility hardening

The selected model's `tools` capability now controls both source-tool and confirmed-action
registration. Previously, globally enabling actions registered `propose_actions` even for
a text-only offering, making an ordinary chat fail before transport dispatch. The native
regression covers all four combinations of model tool support and action enablement.

The adapter rehearsal sends the same source-read and typed page proposal through a scripted
model and the supported OpenRouter adapter with mocked HTTP. Both stop at HITL review,
retain owner-scoped source references and keep the synthetic key out of checkpoints.
This is offline contract evidence, not verification of a second real provider.

Full source/action schemas exceed the conservative default 6,000-byte request profile;
the rehearsal explicitly uses the existing 65,536-byte configurable upper bound, including
schema/context overhead. No application/default account limit was increased. A live
activation must choose and approve a profile budget that fits its actual enabled tools.

## Disposable recovery proof (2026-10-26)

Two additional native regressions cover interrupted document-attempt accounting/lease
fencing and embedding-generation replacement with lexical fallback. The document and
semantic-index files passed **14 tests** on the disposable PostgreSQL target.

A separate manual proof used Docker network `ukladen-ai09-tests` with `--internal`,
synthetic credentials, PostgreSQL 18/pgvector and Redis 7.4. No production mounts or
provider catalog were supplied. The test model was explicitly fake.

- Seeded a real framework checkpoint, confirmed page proposal, independent execution
  receipt, committed page, encrypted personal connection and queued full-source run
  in disposable database `ai09_proof`.
- Ran PostgreSQL `pg_dump -Fc` and `pg_restore --exit-on-error` into a separate empty
  `ai09_restored` database. Kept the synthetic encryption keyring outside the SQL dump.
- Verified restored credential decryption, continued the checkpointed conversation
  and repeated the exact confirmation: its stored target remained unchanged and only
  one business page existed. This tests backup consistency, not a production backup.
- Started an actual Celery solo worker on the dedicated `ai-documents` queue and
  terminated it with exit 73 inside the fake model, after attempt admission and before
  a result. The durable run/lease survived.
- Restarted the separate proof Redis and deliberately cleared its disposable database
  0, removing queued/unacknowledged state. The regression Redis used by pytest was separate.
- Expired only that synthetic job's lease to avoid a two-minute wait, started a fresh
  worker and invoked the normal PostgreSQL-backed document dispatcher. The dispatcher
  repopulated the lost queue; the new worker completed every character of the source.
  Exactly one attempt remained interrupted with unknown tokens. Late-lease rejection
  and duplicate final-result protection are covered by the native regressions.

For repetition, use fresh disposable databases and preserve their corresponding synthetic
keyring together with the custom-format dump. Restore into an empty target; validate
checkpoint continuation, receipt replay and decryption through application services.
Exercise worker/broker failure on dedicated test containers only. Broker state is not
an authoritative backup and cannot replace database recovery scans. The proof used a
single worker; it is not a production failover or throughput guarantee.
