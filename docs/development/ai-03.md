# AI-03: Authorized Source Reads

Updated: 2026-10-24.
Status: implemented locally; default-disabled, unmigrated and unactivated in the app.
Real-model generation and answer quality remain unverified. Verification is recorded below.

## Owner-approved scope

The owner selected pages, materials, resolved calendar and typed user-database reads;
the agent may search all owned active sources unless the request explicitly restricts
its scope. Missing local evidence permits a separately labeled general explanation.
Important ambiguity requires clarification. Read results carry short source references,
versions, actual coverage and freshness warnings consumed by the [AI-04 UI](ai-04.md).

Calendar questions cover personal/official events with personal overrides and record
dates from active calendar database views. Hidden/skipped events require an explicit
request. Record dates are nonblocking. Relative dates use the current profile timezone.

The owner requested reusable boundaries, not a disposable retrieval implementation.
Search owns evidence contracts; materials owns bounded extracted-text access; AI owns
orchestration and tool registration. AI-05/06 add embeddings/hybrid retrieval behind
these source boundaries. AI-03 does not build a second index or vector pipeline.
Reading a bounded range does not prove full-document or exhaustive-search coverage.
Large-document full-source processing remains AI-06; partial reads are explicit now.

Implementation proceeds autonomously in verified local commits. Substantial scope
changes require a new decision. No application migration, provider traffic, push or
deployment is included.

## Extracted text boundary

MaterialExcerptService checks the active owner and untrashed ready file in the caller's
transaction. ExtractedTextReader returns at most 2000 Unicode characters starting at
a zero-based character offset and the extracted text's total character count. The SQL
adapter slices in PostgreSQL, rechecks owner/status/trash and does not download binary
originals or fetch bookmark URLs. Missing extraction differs from an empty ready text.
Offsets refer to extracted text, not original PDF page numbers. Versions are canonical
material versions; extraction and metadata are published in the same transaction.

## Tools and evidence

Tool-capable selected model offerings receive seven typed LangChain tools. The default
fake demonstration retains its synthetic tool; text-only real offerings get no source
tools. No business write, arbitrary HTTP/SQL, binary download or web tool is registered.

| Tool | Delivered behavior |
| --- | --- |
| search_workspace | Existing lexical search, optional page/material type and up to 20 explicit source IDs, 1–8 snippets and bounded offset |
| read_page | Current untrashed page or selected block, derived Markdown, at most 2000 Unicode characters, source version and range |
| read_material_excerpt | Current ready extracted text through the material-owned boundary; no OCR or remote URL fetching |
| get_calendar_events | Resolved official/personal event summaries and deduplicated record dates, profile timezone, source freshness warnings, pagination |
| list_databases | Bounded discovery of current active owned databases |
| read_database | Paginated property/view discovery; select property_id to paginate that property's options |
| query_database | Existing typed filters/sorts/columns or an unchanged saved table view; no saved-view mutation |

EvidenceResult is a provider-neutral envelope with status, bounded JSON data, source
references, complete/partial/none coverage, warnings and nullable next_offset. One
serialized result is limited to 16 KiB. Errors distinguish not_found, not_ready,
unavailable, invalid and limit; failure is never a successful empty search. Lexical
results always disclose partial coverage. Complete applies to the requested range or
selection, never implicitly to the original binary or all workspace knowledge.
Page locations refer to derived Markdown, material locations to extracted Unicode
character ranges. No original PDF page/slide locations are invented. Future chunk
retrieval can return the same evidence envelope with real version/location metadata.

Each source operation uses an independent read-only repeatable-read transaction with
a five-second PostgreSQL statement timeout. Model execution holds no source transaction.
Existing ten-second tool and sixty-second run bounds still apply. Source construction
has no upstream IIS, LLM, S3 or bookmark-fetch side effects. Owner/profile/run access
is checked at the normal application and dispatch boundaries.

Calendar discovery examines at most 200 active databases, 200 views per examined
database and 20 selected calendar views. Reaching a discovery bound emits a partial
coverage warning; explicit missing/foreign/invalid views fail rather than silently
vanishing. Entries are bounded/paginated; hidden/skipped events require include_hidden.
Record dates remain nonblocking. Display completeness is never availability/coverage
proof. Official reference versions follow the existing resolver: zero means no personal
override, not an upstream revision fingerprint; current reads do not rely on that zero.
Event summaries include title, interval, location, busy/hidden/skipped/override flags
and version. Descriptions are explicitly omitted with a warning, so a long description
cannot prevent reading the day's event list. Record-date projection fields are retained.
Database schemas and property options have independent bounded pagination through the
same read_database tool; large option lists do not require an unbounded schema response.

## Scope and current conversation context

Message submission optionally accepts source_scope with page_ids, material_ids,
database_ids (at most 20 IDs combined) and calendar (default false). Omission permits
all owned active sources. An empty scope permits no source reads. Tools cannot override
this server-bound selection or user identity. Search within a mixed explicit scope
must select page/material type separately. Page bodies require explicit page scope;
database scope permits schema/record queries, not an implicit expansion to page bodies.
Natural-language source-only requests are also part of the assistant policy; a client
that needs a hard scope boundary supplies source_scope explicitly on each submission.
Selected IDs are not grants to another owner's data. Scope participates in submission
idempotency; omitted scope preserves the existing digest contract.

Before every model dispatch, middleware rebuilds the newest eight delivered source
queries through current application services, including during the same run. Rebuilt
source envelopes have a 48 KiB total ceiling, with newest evidence taking priority.
Older/oversized evidence becomes an explicit limit result. Reconstruction is internal
source validation, not replay of a model/provider call or a business write. It neither
adds provider attempts nor advertised tool invocations to the model-triggered ledger.

The outgoing model context replaces old tool bodies and suppresses prior source-based
assistant prose, including later summaries derived from earlier source evidence.
Generated tool-call prose/arguments are not forwarded as source truth. Original user
messages remain user input. Reused provider call IDs are matched within their actual
message position. Conflicting versions of the same source during context construction
produce unavailable evidence, not mixed-version excerpts. Refresh always reapplies
current scope, owner, active/trash state, versions and calendar warnings. Changes after
the dispatch snapshot cannot retroactively retract already sent provider context.

## Source references and migration

Alembic revision 0025_ai_message_sources adds a default-empty JSONB sources column to
ai_messages. Only assistant messages can hold references, at most 64 and 64 KiB. The
repository writes typed references with the answer and completion transaction. Existing
messages retain content and gain an empty list. Downgrade takes an exclusive lock and
refuses retained nonempty source metadata. Migration was applied only to disposable
test schemas, never to the running app.

Message history returns sources containing source kind, ID, version, title, locator and
optional parent database ID. These are historical references to evidence supplied at
generation, not a current-access token or a guarantee of generated claim correctness.
Tool bodies stay in owned checkpoints; no source bodies enter content-free run journals.
References follow the existing chat retention/deletion cascade. The assistant is guided
to use [source:id] citations; source navigation/rendering is implemented by the [AI-04 UI](ai-04.md).

Operator input bounds cover the whole serialized provider request, including schemas
and history. The configurable ceiling is now 65536 bytes; the existing 6000-byte default
is unchanged. The disabled tool-capable example explicitly uses version 2/65536 bytes.
Small private profile budgets or long histories can reject a request before dispatch;
there is no silent truncation or paid/model fallback. This remains the existing bounded
byte contract, not a tokenizer or an unlimited-context promise.

## Verification

Focused offline/native tests cover Unicode ranges, source ownership/trash/version
changes, typed filters, calendar record projection, preserving source migrations,
bounded tool schemas, explicit scope, actual synthetic HTTP tool exchange, stored
references, idempotency, inherited stale summaries and reused provider call IDs.

remain outside this slice. Final backend regression results follow.
