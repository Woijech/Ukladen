# AI-05: Local CPU Embedding Runtime

Status: implemented and verified locally, including synthetic hardware proof and
native regression checks. No application
activation, search index, retrieval jobs or production embedding endpoints are added.
AI-06 owns versioned chunks, indexing lifecycle and hybrid retrieval.

## Runtime and boundary

`search.application.embeddings.EmbeddingProvider` is a synchronous application port
returning ordinary float tuples and an explicit model profile. SDK types remain in
the integration. Another local model or an API can implement this port later;
new models require a separate index generation and re-embedding under AI-06, even
when dimensions match. Canonical page/material content is preserved. External API
processing, account quotas and costs require their own approval/activation gate.

The first implementation uses `intfloat/multilingual-e5-small`, revision
`614241f622f53c4eeff9890bdc4f31cfecc418b3`, and its published FP32 ONNX export.
The tokenizer has the same revision. Files are verified against pinned byte sizes
and SHA-256 digests before loading; no custom model code is executed.

Model contract: 384 dimensions, attention-mask-aware mean pooling followed by L2
normalization, `query: ` and `passage: ` prefixes including non-English input, and
512 tokens including prefix/special tokens. Oversized text is rejected rather than
silently truncated. Document splitting belongs to AI-06. Input is bounded to one
query or four documents and 16 KiB UTF-8 per text. Empty/NUL/invalid Unicode input,
nonfinite/zero vectors and unexpected output shapes are rejected.

An instance lazily loads one model on first use. A nonblocking instance lock admits
one inference/load at a time; saturation fails without queuing. Async callers must
offload the synchronous operation. ONNX uses CPU only, two intra-op threads,
sequential execution and disabled spinning/telemetry. Tokenization runs serially.
Ordinary API/workers do not import the optional runtime or load a model.

## Dependencies and artifacts

The `embeddings` extra pins ONNX Runtime 1.31.0, tokenizers 0.23.3 and NumPy 2.5.4.
The existing stack has no tensor inference/tokenizer implementation. These libraries
provide CPU inference, the model's actual tokenizer and pooling; they add native
wheels and model lifecycle management, without PyTorch, CUDA or a serving service.
Normal installs/images omit this extra. Backend CI installs it for synthetic unit
tests and never downloads the model or calls a real provider.

From `apps/backend`, after authorizing the public package/model downloads:

```bash
uv sync --frozen --extra embeddings
uv run --no-sync python -m app.integrations.embeddings.artifacts /absolute/model/directory
```

The explicit downloader fetches only the two pinned public artifacts (487,351,240
bytes combined), verifies each before atomic publication and cleans partial files.
Existing mismatched files fail closed. Inference is local-file-only: it never calls
the downloader, Hugging Face inference or another provider. Mount artifacts read-only.

`docker build --target embeddings` selects the optional CPU image; the default
Docker target remains the ordinary backend without embedding dependencies.

## Reproducible disposable proof

`benchmarks/embedding_runtime.py` is operator tooling, outside the application wheel.
The proof-only API adds synthetic endpoints to the normal FastAPI app; the other
process simulates indexing batches. Both reuse the real adapter. No product route,
Celery embedding queue or persistent index is delivered by this proof.

The Compose overlay uses `.env.example`, disables schedule/AI/provider activation,
uses an internal network, read-only model mounts and 2 GiB limits on each model
process. Ordinary workers load no model. Always use the separate project name below;
never apply this overlay to an application deployment or reuse application volumes.

From the repository root, after downloading the verified artifacts:

```bash
export AI_PROOF_MODEL_DIRECTORY=/absolute/model/directory
docker compose --env-file .env.example -p ukladen-ai05 \
  -f docker-compose.yml -f docker-compose.embedding-proof.yml \
  up --build --detach --wait --wait-timeout 180
docker compose --env-file .env.example -p ukladen-ai05 \
  -f docker-compose.yml -f docker-compose.embedding-proof.yml exec -T api \
  python /proof/embedding_runtime.py measure --api http://api:8000 \
  --worker http://embedding-proof-worker:8000 --duration 30 --query-interval-ms 100
docker compose --env-file .env.example -p ukladen-ai05 \
  -f docker-compose.yml -f docker-compose.embedding-proof.yml exec -T api \
  python /proof/embedding_runtime.py quality /model
```

Measurement requires fresh API/worker processes, measures a baseline then simultaneous
queries/indexing, and fails on unsuccessful requests/worker errors instead of reporting
only successful samples. Each instance serializes inference; the query producer waits
100 ms after each response (less than ten queries/second), while indexing runs continuously
with batch four and two CPU threads. Use `--query-interval-ms 0` for saturation.
The synthetic worker stops after at most 150 seconds even if the controller disappears.

The output includes cold first-call times, warm p50/p95, indexing throughput, process
RSS/high-water/swap, host memory/swap activity, CPU utilization and the actual live/ready
API p95 change. Repeat with fresh processes to obtain a cold distribution; model files
may remain in the OS page cache. These are measurements on an otherwise active personal
computer, not production capacity promises. The quality command covers six synthetic
topics and twelve Russian/English queries; it is not a representative retrieval evaluation.

For another measurement, restart only the proof API/worker and wait for health before
running `measure`. For cleanup, run the same Compose command with `down --volumes`
instead of `up`; this deletes only the disposable project's volumes. Model downloads
remain in the operator-selected directory.

## Verification status

### Hardware results (2026-10-25)

Measured on AMD Ryzen 7 7735HS (8 cores / 16 threads), approximately 14.9 GiB RAM,
Linux x86-64 and Python 3.14.4. The disposable stack included PostgreSQL 18/pgvector,
Redis, SeaweedFS, normal Celery/material workers, Beat, frontend and Traefik. Two
separate model processes used two intra-op threads each and batch four for indexing.
Each run had a 30-second baseline and 30 seconds of simultaneous load.

| Measurement | Saturation, no pause | Bounded run 1 | Bounded run 2 |
| --- | --- | --- | --- |
| Query count in loaded phase | 2900 | 270 | 270 |
| Warm query p50 / p95, milliseconds | 10.21 / 12.70 | 11.15 / 13.20 | 11.10 / 13.25 |
| Indexing documents/second | 10.73 | 11.72 | 11.68 |
| Live API p95 change | +7.87% | -11.19% | -0.23% |
| Ready API p95 change | +28.08% | -7.53% | -6.02% |
| Host CPU busy, loaded phase | 30.2% | 18.5% | 18.9% |
| Minimum host available RAM | 5.13 GiB | 5.28 GiB | 5.24 GiB |
| Host swap-in / swap-out pages | 1071 / 3236 | 2 / 0 | 23 / 0 |

Bounded runs waited 100 ms after each query response (about nine requests/second).
Negative API changes are sampling/background-load variation, not a speedup claim.
The ready endpoint checked real PostgreSQL, Redis and S3; p95 was 5.25–5.34 ms under
bounded load versus 5.59–5.77 ms baseline. Saturation raised it from 5.65 to 7.24 ms.

Across three fresh-process samples, cold query p50/p95 was 1.885/1.982 seconds and
cold indexing-batch p50/p95 was 2.147/2.431 seconds, including artifact verification
and lazy initialization. Three samples do not establish a production tail guarantee;
OS file-cache eviction was not forced. Both model processes stayed below their
2 GiB container limits: API RSS about 1046 MiB/high-water 1359 MiB; index worker RSS
about 982 MiB/high-water 1203 MiB. Process `VmSwap` remained zero. Both cgroups
reported zero OOM/OOM-kill/max-limit events. Bounded phases had no host swap-out;
the saturation phase did have host swap activity on the shared computer.

The synthetic ranking smoke returned top-1 matches for 11/12 queries: Russian 6/6,
English 5/6. The English functional-dependency query ranked its expected database
document third. This is insufficient evidence for real-material retrieval quality;
AI-06 must evaluate chunking, lexical/vector fusion, permissions and coverage.
Query samples were 13–22 tokens; indexing documents were 235–316 tokens. A separate
real-tokenizer check accepted exactly 512 tokens (single query about 168 ms) and
rejected input beyond that boundary instead of truncating it.

Decision: retain the pinned optional ONNX CPU candidate for AI-06. The documented
bounded workload meets the initial warm-query/API-impact targets without sustained
swapping/OOM. Continuous saturation fails the <=20% API-impact target; production
admission/load limits must be proved with actual AI-06 traffic before activation.
There is no automatic remote fallback or promise of unlimited hardware throughput.

### Executed checks

- Ruff lint/format and Pyright passed; 23 synthetic adapter/proof tests passed.
- Both default and optional Docker targets built. The default image had no NumPy,
  ONNX Runtime or tokenizers; importing/constructing the adapter did not load a model.
- Real CPU inference also passed with Docker networking disabled entirely.
- Base and proof-overlay `docker compose config --quiet` passed.
- Full backend regression passed: 1756 tests, no skips, against separate disposable
  PostgreSQL/Redis/S3 targets (483.62 seconds). One harmless pytest cache-permission
  warning occurred in the non-root disposable test container. Earlier host verification
  passed 1103 tests with 648 native-service skips before proof tests were added.

Frontend files were unchanged; frontend checks were not rerun. No real provider
account, production data/migrations, production activation or AI-06 index was used.
