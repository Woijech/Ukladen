# User Avatar API

Status: implemented, backend only.

The users module supports one private avatar for the current authenticated user.
Image bytes live in the existing S3-compatible bucket (SeaweedFS locally).
PostgreSQL stores only the nullable `users.avatar_key` reference; the owner is the
user row. The normalized format is always PNG and the dimensions are always
512 × 512, so additional content-type or dimension columns are unnecessary.

## API

| Endpoint | Behavior |
| --- | --- |
| `PUT /api/v1/users/me/avatar` | Accepts raw image bytes, validates/normalizes them, replaces the avatar, and returns the full profile DTO with HTTP 200 after commit. |
| `GET /api/v1/users/me/avatar` | Returns the current user's image as `image/png`, or 404 when absent. |
| `DELETE /api/v1/users/me/avatar` | Clears the avatar reference and returns an empty 204 after commit. Repeating deletion is safe and does not update timestamps when already absent. |

All endpoints require the existing active opaque-cookie session. PUT and DELETE
also require the existing CSRF cookie/header and exact allowed Origin. Canonical
active-user eligibility is rechecked under a PostgreSQL row lock, including reads,
so replacement cleanup cannot race an avatar download. Unverified active users
and Google-only accounts follow the existing authentication policy. The session
determines the owner; clients cannot supply a target user ID, object key or remote
image URL. Profile patches reject avatar fields and preserve the avatar reference.

Uploads use a raw request body with exactly `Content-Type: image/jpeg`,
`image/png` or `image/webp`. Multipart forms are not accepted. A bounded request
stream limits uploads to 2 MiB, including chunked requests. Images may contain at
most 4,194,304 decoded pixels. Empty, malformed, truncated, animated, mismatched
content-type and unsupported images (including SVG/GIF) are rejected. Pillow
verifies and fully decodes the supported image, applies EXIF orientation, crops
and resizes it to a square, and copies its pixels into a fresh PNG. Input EXIF,
ICC, text and other metadata are discarded. CPU/image work and synchronous
database/storage work run in the thread pool rather than the async event loop.

`GET /api/v1/users/me` and successful profile/avatar updates return an additional
`avatar_url`: null when absent, otherwise `/api/v1/users/me/avatar`. This is a
relative authenticated API URL, never a public S3 URL or storage key. The current
API supports only the current user's avatar; public/other-user lookup is not
implemented. Avatar responses and errors use `Cache-Control: no-store`; image
responses also set `X-Content-Type-Options: nosniff`.

| Status | Meaning |
| --- | --- |
| `200` | Uploaded profile response or PNG image. |
| `204` | Avatar removed or already absent. |
| `401` | Invalid/expired/revoked session or missing/disabled user; existing auth cookie clearing applies. |
| `403` | Invalid CSRF protection or missing/disallowed Origin. |
| `404` | No current avatar or its stored object is absent. |
| `413` | Upload exceeds the byte or decoded-pixel limit. |
| `422` | Invalid avatar image; no input is echoed. |
| `503` | Database/write/commit or storage failure; no SDK/connection details are exposed. |

## Storage and transaction behavior

Object keys are generated by the server as `avatars/<user UUID>/<random UUID>.png`.
Each upload uses a fresh key. PostgreSQL enforces both the key format and its user
ownership. Users never choose bucket/object names, and raw credentials or image
data are not logged. The configured bucket must remain private.

Avatar mutations lock the active user until the caller's database transaction
finishes. Upload stores the normalized object, then changes only `avatar_key` and
`updated_at`. Concurrent profile/avatar updates preserve other fields. Successful
replacement/removal deletes the previous object only after commit. A failed write
or aborted commit preserves the previous reference/image and attempts to remove
the newly uploaded object. After database errors, compensation checks the canonical
reference under a row lock using an independent connection. If commit acknowledgement
was lost but the new reference was committed, its object is retained. If the
database cannot establish the commit outcome, compensation retains the object.

S3 and PostgreSQL are separate systems. A process crash, unavailable cleanup
storage, or uncertain database state can leave an unreferenced object. Cleanup is
best effort and logs only a fixed event/message; a cleanup failure after a successful
commit does not reverse the profile update or delete its current image. Durable
orphan recovery is not implemented. A committed operation with a lost acknowledgement
can return 503 even though its reference persisted; read the profile to establish
the current state. This avoids deleting a valid image under an ambiguous commit.

The API lifespan owns and closes `S3AvatarStorage`. It uses the existing
`S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` and `S3_BUCKET`. No credentials or
deployment volumes were changed. boto3 handles S3 signing and transport; the
standard library and existing HTTP client do not provide a signed S3 client.
The transport configuration follows the [SDK configuration contract](https://docs.aws.amazon.com/botocore/latest/reference/config.html).
The adapter uses SigV4, path-style requests, the `us-east-1` signing region,
three-second connect/read timeouts, at most two attempts, and optional checksums
only when required for S3-compatible server support. Pillow supplies real image
decoding/verification and normalization, which the existing stack lacks, using
[Pillow image operations](https://pillow.readthedocs.io/en/stable/reference/ImageOps.html). Both
dependencies are locked in `uv.lock`; no multipart parser, generic file pipeline,
new worker job or storage service was added.

## Migration

`0004_users_avatar` follows `0003_users_profile`, adding only a nullable string
reference and ownership/format check constraint. Existing user/profile/auth data,
timestamps and registration contracts are preserved. Existing accounts start with
no avatar. Downgrade to `0003_users_profile` removes only the reference/constraint;
it does not contact object storage or delete images. Those images become unreferenced.
The normal migration command applies the change:

```bash
cd apps/backend
uv run --env-file ../../.env alembic upgrade head
```

## Usage

Run the [profile example](user-profile.md) through login, keeping its cookie jar
until the avatar requests finish. With the same `profile_origin`,
`profile_cookie_jar` and `profile_csrf` variables:

```bash
curl --fail --silent --show-error -b "$profile_cookie_jar" \
  -H "Origin: $profile_origin" -H "X-CSRF-Token: $profile_csrf" \
  -H 'Content-Type: image/png' -X PUT --data-binary @avatar.png \
  "$profile_origin/api/v1/users/me/avatar"

curl --fail --silent --show-error -b "$profile_cookie_jar" \
  "$profile_origin/api/v1/users/me/avatar" --output current-avatar.png

curl --fail --silent --show-error -b "$profile_cookie_jar" \
  -H "Origin: $profile_origin" -H "X-CSRF-Token: $profile_csrf" \
  -X DELETE "$profile_origin/api/v1/users/me/avatar"
rm "$profile_cookie_jar"
```

PUT returns the profile with `avatar_url: "/api/v1/users/me/avatar"`. GET downloads
the normalized PNG. DELETE returns 204, and the next profile GET has a null URL.
Use the actual MIME type for JPEG/WebP files. Swagger documents the binary request
types; OpenAPI remains at `/api/openapi.json`.

## Verification

The `test_users_avatar*.py` checks cover image formats, metadata/orientation,
animation and pixel/byte limits, malformed/mismatched content, authentication,
CSRF, ownership, independent-session persistence, profile/auth preservation,
write/commit/delete failures, uncertain commits, storage failures, safe cleanup
logs, concurrent updates/replacement, SDK request/error behavior and migration
upgrade/downgrade. Existing profile tests also assert protected avatar fields.

Use the existing `AUTH_TEST_DATABASE_URL` and `AUTH_TEST_REDIS_URL` integration
settings. The native SeaweedFS check additionally requires these variables against
disposable test storage with an existing private bucket:

```bash
export AVATAR_TEST_S3_ENDPOINT='http://localhost:58333'
export AVATAR_TEST_S3_ACCESS_KEY='YOUR_TEST_ACCESS_KEY'
export AVATAR_TEST_S3_SECRET_KEY='YOUR_TEST_SECRET_KEY'
export AVATAR_TEST_S3_BUCKET='YOUR_TEST_BUCKET'
uv run pytest
```

The native check creates/deletes only generated keys; it does not create or remove
the bucket. It skips when the S3 test endpoint is unset. PostgreSQL schemas and
Redis keys retain the existing isolation/cleanup behavior. Tests send no external
email or Google requests.
